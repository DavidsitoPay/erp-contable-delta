# Implementación de DevOps en la Empresa

Este documento describe la implementación de prácticas de DevOps en el proyecto Delta ERP Contable (DEC), desarrollado para el curso Seminario de Tecnologías de Información (UMG, 2026) por el equipo integrado por David Edgar Recinos García (Product Owner), Alejandro Rocael Ochoa Pérez (Scrum Master), José Rodolfo López y López y Luis David Reyes Mijangos (equipo de desarrollo). Corresponde a la entrega de DevOps 2, que amplía la infraestructura base configurada en DevOps 1 con un flujo de integración y despliegue continuo funcional, validado mediante ejecuciones reales.

El alcance funcional del sistema al momento de esta entrega cubre los módulos de catálogo contable, registro de asientos y seguridad/autenticación (M1, M2 y M8 del backlog de producto), que son los módulos priorizados como prerrequisito del resto del sistema. Los módulos restantes (libros auxiliares, cuentas por cobrar y por pagar, tesorería, reportes e importación) quedan diseñados en la documentación de arquitectura y reglas de negocio, pero no forman parte del incremento entregado. Esta decisión de alcance se explica con mayor detalle en la sección de reflexión sobre Scrum, y responde a una reducción deliberada de la capacidad efectiva del equipo durante los últimos sprints, priorizando la calidad y el funcionamiento correcto de lo entregado sobre la cobertura completa del backlog original.

## Objetivo de la implementación

El objetivo de esta implementación es resolver un problema concreto detectado durante DevOps 1: la infraestructura del proyecto existía, pero su actualización dependía de pasos manuales no documentados ni repetibles, lo que introducía riesgo de desincronización entre el código fuente, el esquema de base de datos y lo realmente desplegado. Cada cambio en el backend o en la base de datos requería que una persona recordara y ejecutara manualmente una secuencia de comandos para aplicar migraciones, reconstruir la imagen y actualizar el servicio en la nube.

La implementación de DevOps busca eliminar esa dependencia de procesos manuales mediante automatización: que cada cambio fusionado a la rama principal del repositorio dispare, sin intervención humana, la validación del esquema de base de datos, la construcción de la imagen del backend, su publicación en un registro de contenedores y su despliegue en el servicio en la nube correspondiente. Los beneficios esperados son cuatro: integración continua real entre código y base de datos (ningún cambio de esquema queda pendiente de aplicar a mano), despliegue consistente y reproducible (la misma secuencia de pasos se ejecuta siempre, sin variación entre ejecuciones), calidad verificada de forma automática mediante análisis estático de código, y continuidad del servicio, entendida como la capacidad de detectar y revertir un despliegue defectuoso antes de que afecte al ambiente que usan los usuarios finales.

## Herramientas utilizadas

El control de versiones y la orquestación del flujo de integración y despliegue continuo se realizan sobre GitHub, usando GitHub Actions como motor de automatización: ejecuta los flujos de trabajo definidos en formato YAML cada vez que se fusiona un cambio a la rama principal. La imagen de contenedor del backend se construye con Docker a partir de un Dockerfile de dos etapas (compilación y ejecución) y se publica en GitHub Container Registry (GHCR), el registro de contenedores integrado a GitHub. El backend se ejecuta en Azure Container Apps, un servicio de contenedores administrado que expone la API mediante un dominio público y escala automáticamente el número de réplicas según la demanda, incluyendo la posibilidad de escalar a cero instancias en ausencia de tráfico. El frontend, una aplicación de una sola página construida con React, se despliega en Vercel, una plataforma especializada en aplicaciones web estáticas y de frontend con integración nativa a GitHub. La base de datos PostgreSQL se aloja en Neon, un proveedor de PostgreSQL sin servidor que permite mantener ramas de base de datos independientes (producción y desarrollo) derivadas de un mismo esquema. La autenticación entre GitHub Actions y Azure se realiza mediante OpenID Connect (OIDC), sin credenciales de larga duración almacenadas como secreto. La calidad del código se valida con SonarCloud, integrado como verificación automática sobre cada cambio propuesto al repositorio. La planificación del proyecto bajo Scrum se documenta en Azure Boards. Azure Pipelines se mantiene como una segunda herramienta de integración continua, con un alcance reducido a la verificación de compilación del backend y del frontend, según se explica en la sección correspondiente al pipeline.

## Creación del grupo de recursos en Azure

Toda la infraestructura de backend del proyecto se agrupa bajo un único grupo de recursos de Azure, de nombre `rg-delta-erp`, que contiene el entorno de Container Apps (`cae-delta-erp`) y la aplicación de contenedor propiamente dicha (`ca-delta-erp-backend`). Agrupar los recursos bajo un mismo grupo permite administrarlos, monitorearlos y, en caso de ser necesario, eliminarlos de forma conjunta, además de facilitar el control de costos dentro de los límites de la suscripción de estudiante utilizada para este proyecto.

## Configuración del servidor de base de datos

El material de referencia de la asignación usa como ejemplo un servidor Azure Database for MySQL Flexible Server. Para este proyecto se sustituyó ese componente por Neon, un proveedor de PostgreSQL sin servidor, por dos razones: el modelo de datos y los procedimientos almacenados del proyecto ya estaban escritos en PostgreSQL desde etapas anteriores del curso, y el nivel gratuito de Neon no depende del crédito por tiempo limitado de la suscripción de estudiante de Azure, lo que da continuidad al proyecto más allá de la vigencia de dicho crédito. La equivalencia funcional entre ambos servicios, dentro del alcance de esta asignación, es directa: un servidor de base de datos administrado, accesible por conexión remota, sobre el cual corre el motor relacional que usa el backend.

Neon organiza el proyecto de base de datos en ramas independientes derivadas de un mismo esquema. Se configuraron dos: `production`, la única ligada al pipeline de despliegue y a la que apunta el backend en Azure Container Apps, y `development`, de uso local para cada integrante del equipo, que el pipeline no modifica. Cada rama expone un punto de conexión directo (no agrupado en pool de conexiones), usado tanto por la aplicación .NET como por el script de migraciones.

## Implementación del servicio de aplicación

El material de referencia usa como ejemplo Azure App Service como servicio único de aplicación. Este proyecto, al tratarse de un frontend desacoplado del backend (arquitectura de aplicación de una sola página consumiendo una API REST), usa dos servicios de aplicación distintos, cada uno especializado en su tipo de carga: Azure Container Apps para el backend y Vercel para el frontend.

El backend se empaqueta como imagen de contenedor mediante un Dockerfile de dos etapas: una etapa de compilación, que restaura dependencias y publica la aplicación .NET en modo Release, y una etapa de ejecución, más liviana, que solo contiene el resultado publicado sobre la imagen base de ASP.NET Core. La aplicación de contenedor se configura con puerto de destino 5000, ingreso externo habilitado, un rango de cero a dos réplicas (permite escalar a cero en ausencia de tráfico, reduciendo el costo a cero cuando el sistema no está en uso) y límites de 0.25 vCPU y 0.5 GiB de memoria por réplica. La cadena de conexión a la base de datos y la clave de firma de tokens JWT se configuran como secretos de la aplicación de contenedor, referenciados desde variables de entorno mediante la sintaxis `secretref`, nunca como texto plano. Los orígenes permitidos de CORS se configuran también como variable de entorno, listando explícitamente los dominios del frontend autorizados a consumir la API.

Durante la operación del proyecto se identificó una limitación real del nivel "Consumption" de Azure Container Apps: una actualización que solo modifica configuración (un secreto o una variable de entorno, sin cambiar la imagen) no siempre se aplica de forma confiable sobre la réplica en ejecución, incluso usando los comandos de actualización o reinicio de revisión provistos por Azure CLI. La solución adoptada, documentada como script versionado en el repositorio (`devops/recreate-containerapp.sh`), es eliminar y volver a crear el recurso completo cuando cambia únicamente la configuración; las actualizaciones que sí cambian la imagen (los despliegues automáticos del pipeline) no presentan este problema y se aplican de forma confiable con `az containerapp update --image`.

El frontend se despliega en Vercel mediante su integración nativa con GitHub: cada push a la rama principal genera un despliegue de producción, y cada push a la rama de desarrollo genera un despliegue de vista previa, sin que sea necesario ningún paso adicional de build o subida manual. Se configuró un archivo de reescritura (`vercel.json`) para que cualquier ruta de la aplicación de una sola página resuelva sobre `index.html`, necesario para que el enrutamiento del lado del cliente funcione al recargar o acceder directamente a una ruta interna.

## Conexión del código con el repositorio

Desde la etapa de DevOps 1 se tomó la decisión de usar GitHub (`DavidsitoPay/erp-contable-delta`) como fuente única del código fuente, evitando mantener una copia sincronizada manualmente en Azure Repos. ## Creación y configuración del pipeline

Para la automatización de integración y despliegue continuo se eligió GitHub Actions en lugar de una herramienta externa como Jenkins o GitLab CI. La justificación es de naturaleza técnica y no arbitraria: el repositorio ya vive en GitHub, por lo que GitHub Actions no requiere vincular una identidad ni un webhook adicional hacia una plataforma externa; no exige aprovisionar ni mantener un servidor o agente propio, lo cual es consistente con la restricción de costo cero del proyecto; y admite autenticación federada (OIDC) directamente contra Azure, evitando almacenar una credencial de larga duración como secreto, algo que Jenkins o GitLab CI habrían requerido resolver con un mecanismo adicional.

Se configuraron dos flujos de trabajo. El primero, `backend-deploy.yml`, se dispara únicamente con cambios en la rama principal que afecten al backend, a la base de datos o al Dockerfile del backend, y está compuesto por dos trabajos encadenados. El primer trabajo, `migrate`, instala el cliente de PostgreSQL y ejecuta el script `database/run_migrations.sh` contra la rama `production` de Neon, aplicando únicamente los scripts SQL que aún no se hayan registrado como aplicados en una tabla de control (`schema_migrations`). El segundo trabajo, `build-and-deploy`, depende explícitamente del primero mediante `needs: migrate`, de modo que si la migración falla, el backend nuevo nunca se construye ni se despliega sobre un esquema que no pudo actualizarse. Este segundo trabajo construye la imagen Docker, la publica en GHCR etiquetada con el hash del commit, se autentica contra Azure mediante OIDC y actualiza la aplicación de contenedor con la nueva imagen:

```yaml
migrate:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - run: sudo apt-get update && sudo apt-get install -y postgresql-client
    - run: bash database/run_migrations.sh "${{ secrets.NEON_PROD_CONNECTION_STRING }}"

build-and-deploy:
  needs: migrate
  steps:
    # build de la imagen, push a GHCR, login OIDC a Azure,
    # az containerapp update --image <imagen>:<sha del commit>
```

El segundo flujo de trabajo, `frontend-alias.yml`, resuelve un problema específico de Vercel: el dominio corto del proyecto (`delta-erp-contable.vercel.app`) no puede administrarse como dominio de proyecto estándar y requiere reapuntarse manualmente a cada nuevo despliegue de producción. Este flujo espera, consultando la API de Vercel, a que el despliegue correspondiente al commit recién subido quede listo, y entonces reasigna el alias corto a ese despliegue mediante una llamada directa a la API REST de Vercel.

Se mantiene además `azure-pipelines.yml`, configurado en DevOps 1, con un alcance reducido de forma deliberada a la verificación de compilación del backend (.NET) y del frontend (React), sin participar en el despliegue real. Se le agregó explícitamente `pr: none` para que la integración de Azure Pipelines con GitHub no se ejecute automáticamente sobre cada Pull Request, evitando que apareciera como una verificación pendiente o en progreso que bloqueara la fusión de cambios en GitHub, duplicando una validación que ya realiza GitHub Actions.

Captura sugerida: el archivo `.github/workflows/backend-deploy.yml` abierto en GitHub (vista de código con resaltado de sintaxis YAML), como evidencia de que el pipeline está versionado dentro del propio repositorio.

Durante la implementación se presentaron fallos reales, cuya identificación y corrección forman parte de la evidencia solicitada. Se documentan aquí cuatro, con la instrucción de que el integrante que los solucionó localice y capture, desde su propio historial de la pestaña `Actions`, la ejecución fallida y la ejecución corregida inmediatamente posterior, junto con el mensaje de error visible en el registro de cada una:

Autenticación federada rechazada (`AADSTS700213: No matching federated identity record found`). Causa: GitHub cambió el formato del identificador de sujeto (`subject`) que emite en sus tokens OIDC para repositorios nuevos, de un formato basado en nombres a un formato inmutable basado en identificadores numéricos de organización y repositorio. La credencial federada configurada en Azure usaba el formato anterior. Corrección: se actualizó la credencial federada en Azure con el nuevo formato de sujeto, usando los identificadores que el propio mensaje de error de Azure reveló.

Fallo de caché en la construcción de la imagen (`Cache export is not supported for the docker driver`). Causa: el controlador de compilación de Docker usado por defecto en el runner de GitHub Actions no admite exportar caché al mismo GitHub Actions. Corrección: se agregó el paso `docker/setup-buildx-action`, que configura un controlador de compilación que sí admite esta función, antes del paso de construcción y publicación de la imagen.

Actualización de configuración sin efecto visible en el backend desplegado. Causa: la limitación de la plataforma descrita en la sección anterior (Azure Container Apps, nivel Consumption, no recicla de forma confiable la réplica activa ante un cambio de solo configuración). Corrección: se documentó y versionó el procedimiento de eliminar y recrear el recurso (`devops/recreate-containerapp.sh`) como única vía confiable para este tipo de cambio.

Fallo del comando `vercel alias set` con error `User not found (404)`. Causa: un comportamiento documentado del CLI de Vercel, que falla una verificación interna de usuario al usar un token de acceso con alcance restringido a un equipo, aunque ese mismo token autentica correctamente contra la API REST de Vercel. Corrección: se sustituyó la dependencia del CLI de Vercel en el flujo de trabajo `frontend-alias.yml` por llamadas directas a la API REST (`POST /v2/deployments/{id}/aliases`), verificadas previamente con el mismo token antes de aplicar el cambio al flujo de trabajo.

## Resultados y evidencias

La consolidación de las evidencias anteriores permite verificar que los componentes configurados operan de forma integrada: un cambio fusionado a la rama principal del repositorio dispara, sin intervención manual, la validación y aplicación del esquema de base de datos sobre el ambiente de producción, seguida de la construcción, publicación y despliegue de una nueva versión del backend; el frontend se despliega de forma independiente mediante la integración nativa de Vercel con GitHub, y su dominio corto se mantiene sincronizado automáticamente con el despliegue de producción vigente; y el resultado observable, verificado mediante pruebas funcionales manuales, es un sistema accesible, con inicio de sesión funcional y persistencia correcta de datos en la base de datos de producción. Los fallos ocurridos durante la implementación fueron identificados a partir de los registros de ejecución del propio pipeline, corregidos, y verificados con una ejecución posterior exitosa, lo que constituye evidencia del propósito de continuidad planteado como objetivo de esta implementación.

## Plan de pruebas

**Objetivo.** Verificar que las funcionalidades implementadas del sistema (catálogo contable, registro de asientos y seguridad) cumplen las reglas de negocio definidas en `docs/business-rules.md`, y que el flujo de integración y despliegue continuo no introduce una versión del sistema que incumpla dichas reglas en el ambiente de producción.

**Propósito.** Reducir el riesgo de que un cambio de código o de esquema llegue al ambiente que usan los usuarios finales sin haber sido validado, combinando verificaciones automáticas dentro del pipeline con verificaciones funcionales manuales guiadas por casos de prueba definidos previamente.

**Alcance.** Se prueban los módulos con estado "Implementado" en el backlog de producto: catálogo y parametrización contable (M1), registro de asientos con validación de partida doble (M2) y seguridad y autenticación (M8). Quedan fuera de alcance de esta ronda de pruebas los módulos con estado "Diseñado" (libros auxiliares, cuentas por cobrar y por pagar, tesorería, reportes e importación), al no existir todavía una implementación ejecutable sobre la cual probar.

**Tipos de pruebas realizadas.** El proyecto no cuenta, a la fecha de esta entrega, con una suite de pruebas unitarias o de integración automatizadas ejecutándose dentro del pipeline; esta es una limitación reconocida del alcance actual, no una omisión no advertida. La validación se realiza mediante dos mecanismos complementarios. El primero son puertas de calidad automáticas integradas al propio pipeline: la migración de esquema (`migrate`) actúa como una prueba de que el esquema de base de datos es válido y aplicable antes de permitir que continúe el despliegue; la compilación de la imagen Docker actúa como una prueba de que el código compila correctamente; y el análisis estático de SonarCloud actúa como una prueba de calidad y seguridad sobre el código propuesto en cada cambio. El segundo mecanismo son pruebas funcionales manuales, ejecutadas sobre el ambiente de producción después de cada despliegue, guiadas por los casos de prueba documentados como work items de tipo Test Case en Azure Boards (`docs/plan-de-pruebas-inicial.md`), enlazados a la Historia de Usuario que verifican y agrupados dentro de un Test Plan formal (ver "Casos de prueba" más abajo). El hub de Test Plans de Azure DevOps, bloqueado por licencia hasta el 23/09/2026, quedó disponible en el nivel gratuito de la organización a partir del 24/09/2026, lo que permitió crear el plan formal sin necesidad de licencia paga ni de activar un trial.

**Casos de prueba.** Se documentaron dieciocho casos de prueba, uno por cada Historia de Usuario del backlog completo, con prioridad de 1 (más alto) a 4. Tres ejemplos representativos de los módulos ya implementados: el caso TC-04 verifica que un asiento contable descuadrado sea rechazado por la API con código 400 y que uno balanceado sea aceptado con código 201, sobre la regla de negocio RN-01; el caso TC-15 verifica que el inicio de sesión devuelva un token JWT válido únicamente con credenciales correctas, rechazando con código 401 una contraseña incorrecta; y el caso TC-16 verifica que un endpoint restringido por rol rechace con código 403 a un usuario sin el rol requerido, y que una acción crítica autorizada quede registrada de forma inmutable en la bitácora de auditoría. Los dieciocho casos están creados como work items de tipo Test Case en Azure Boards, enlazados a su Historia de Usuario correspondiente, y agrupados dentro de un Test Plan formal ("Plan de pruebas - Delta ERP Contable", Plan ID 188) en nueve suites estáticas, una por módulo (M1–M9), dos casos por suite — verificado directamente contra el proyecto real (organización `drecinosg2`, proyecto `erp-contable-delta`) el 24/09/2026, incluyendo una lectura de cada suite de vuelta contra la API para confirmar que los 18 casos quedaron asignados y ninguno huérfano.

**Estrategia de pruebas.** Dado que el sistema no expone un ambiente de prueba separado del de producción (no existe, por diseño, un ambiente de staging adicional dentro del alcance de costo cero del proyecto), la estrategia adoptada es ejecutar los casos de prueba manualmente contra el ambiente de producción inmediatamente después de cada despliegue, antes de considerar cerrado el ciclo de integración de un cambio, complementada por las puertas de calidad automáticas descritas arriba que sí corren en cada ejecución del pipeline sin intervención manual.

**Ejecución del plan de pruebas.** Las puertas de calidad automáticas se ejecutan en cada push a la rama principal, como parte del flujo de trabajo `backend-deploy.yml`. Las pruebas funcionales manuales se ejecutan después de cada despliegue verificado como exitoso, a cargo del integrante que realizó el cambio, y sus resultados se registran dentro del Test Plan (Plan ID 188), marcando cada Test Case como Pass o Fail en su suite correspondiente, además del comentario habitual en el work item.

**Parámetros del sistema.** El backend corre sobre .NET 8 (SDK y runtime ASP.NET Core), compilado en configuración Release. El frontend se compila con Node.js 20 y Vite, y se sirve como archivos estáticos. La base de datos es PostgreSQL, administrada por Neon en su nivel sin servidor. La aplicación de contenedor del backend está limitada a 0.25 vCPU y 0.5 GiB de memoria por réplica, con un rango de cero a dos réplicas. La autenticación de la API usa tokens JWT firmados con una clave simétrica almacenada como secreto. Los orígenes permitidos de CORS se restringen explícitamente a los dominios conocidos del frontend desplegado.

## Reflexión sobre la aplicación de SCRUM en la transformación digital

La aplicación de Scrum en este proyecto organizó el trabajo del equipo en roles diferenciados desde el inicio: un Product Owner responsable de priorizar el backlog y validar criterios de aceptación, un Scrum Master responsable de facilitar el flujo del equipo y mantener actualizado el seguimiento del sprint, y un equipo de desarrollo responsable de la construcción técnica. Esta distribución de responsabilidades permitió, durante el primer sprint, dividir el trabajo por especialidad (base de datos, configuración de DevOps, backend) sin bloqueos entre integrantes, según se registró en la retrospectiva correspondiente.

El seguimiento de actividades mediante Sprint Backlog con tareas acotadas a un máximo de dieciséis horas y un burndown chart actualizado periódicamente hizo visible, con varios días de anticipación al cierre del sprint, una desviación entre el avance planificado y el avance real, originada en una corrección del modelo de datos solicitada como retroalimentación del catedrático. Esa visibilidad temprana es, en sí misma, uno de los aportes centrales de Scrum a un proyecto de transformación digital: convierte un problema que en un esquema de entrega única solo se habría detectado al final en una decisión que el equipo puede tomar a tiempo.

Esa misma visibilidad es la que permitió gestionar, en sprints posteriores, un cambio más significativo: la disponibilidad efectiva del equipo de desarrollo se redujo respecto de la planificación original. Frente a esa situación, la alternativa de mantener el alcance completo del backlog original habría implicado comprometer la calidad o la corrección técnica de los módulos entregados, algo que la naturaleza incremental de Scrum no exige aceptar. En su lugar, el Product Owner reevaluó y redujo el alcance de la entrega a los módulos que podían completarse con un nivel de calidad verificable, dejando el resto del backlog documentado y diseñado, pero no implementado. Esta es una gestión de cambio deliberada y explícita, apoyada directamente en el principio de Scrum de priorizar valor entregado y verificado sobre cobertura nominal de requerimientos, y no una desviación no planificada del proceso.

Esa decisión es verificable en la propia herramienta de planificación, no solo en esta narrativa: Azure Boards mantiene los tres Sprints planificados desde el inicio del proyecto (Sprint 1, cerrado el 21/09; Sprint 2, en curso; Sprint 3, planificado hasta el 19/10), con los nueve Epics, sus nueve Features y sus dieciocho Historias de Usuario distribuidos entre los tres y estimados en horas, aunque únicamente los Epics de los módulos M1, M2 y M8 alcanzaron el estado Done. El backlog restante no se eliminó ni se reescribió para ocultar la reducción de alcance; permanece visible en su estado real de avance dentro de la misma herramienta que documenta la planificación del proyecto.

La comunicación entre integrantes, documentada mediante el formato de tres preguntas del Daily Scrum (qué se hizo, qué se planea hacer, qué impedimentos existen), funcionó de forma efectiva mientras la participación del equipo completo fue constante; su valor disminuyó proporcionalmente a la disponibilidad real de cada integrante en las últimas semanas del proyecto, lo que confirma que Scrum facilita la comunicación entre quienes participan activamente, pero no sustituye la necesidad de esa participación. En cuanto a identificación y solución de problemas, el propio pipeline de integración continua actuó como un mecanismo adicional de retroalimentación rápida, señalado ya en la retrospectiva del primer sprint como algo que funcionó bien: detectó errores reales (de configuración, de autenticación federada y de compatibilidad de herramientas, documentados en la sección de ejecución del pipeline) en el momento en que se introducían, en lugar de acumularse sin detectar hasta una etapa posterior del proyecto.

En conjunto, el aporte de Scrum a este proceso de transformación digital no fue evitar los problemas de planificación o de capacidad del equipo, que ocurrieron de todas formas, sino hacerlos visibles con suficiente anticipación como para responder a ellos mediante decisiones deliberadas de alcance y priorización, en lugar de mediante una entrega final que ocultara esas decisiones hasta el último momento.
